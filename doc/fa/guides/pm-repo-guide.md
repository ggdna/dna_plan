# راهنمای مخزن مدیریت پروژه

## بدان مخزن PM چیست <a id="know-what-a-pm-repo-is"></a>

- مخزن مدیریت پروژه (PM repo) هدف‌ها، نیازمندی‌ها، مفهوم‌ها، برنامه‌ها،
  زمان‌بندی، جلسه‌ها، تصمیم‌ها و پست‌های وبلاگ یک پروژه را نگه می‌دارد — نه
  کد
- هر تیکت دقیقاً به یک مخزن PM تعلق دارد. آن را پیش از هر مخزن کدی به
  تیکت اضافه کن (راهنمای توسعهٔ `gg` را ببین)
- تیکتی که فقط برنامه‌ریزی می‌شود فقط با مخزن PM به پایان می‌رسد
- نیازمندی‌ها پیش از تیکت‌ها می‌آیند: ابتدا آن‌ها را با کاربر استخراج کن،
  [اول نیازمندی‌ها را استخراج کن](#engineer-the-requirements-first) را ببین
- هر فایل را در هر زبان مخزن نگه دار،
  [زبان‌ها را نگه دار](#keep-the-languages) را ببین

## مخزن را این‌گونه ساختار بده <a id="structure-the-repo-like-this"></a>

```text
root
|-doc
| |-en
| | |-guides
| | |-templates
| |-de
| | |-...
|-pm
| |-en
| | |-2026-Q3
| | | |-architecture
| | | | |-architecture.md
| | | | |-img
| | | |    |-diagram.mmd
| | | |-blog
| | | | |-2026-09-10-blogpost-1.md
| | | |-bugs
| | | |-charts
| | | | |-schedule.md
| | | |-concepts
| | | | |-decisions
| | | | | |-000-index.md
| | | | |-topics
| | | | |-ux
| | | |-exports
| | | | |-2026-09-10-anna-sprint.csv
| | | |-goals
| | | | |-results-without-desktop-software.md
| | | |-meetings
| | | | |-2026-09-08-kick-off.md
| | | |-prompts
| | | |-reports
| | | | |-anna.md
| | | |-requirements
| | | | |-results.md
| | | |-team
| | | | |-people.md
| | | | |-roles.md
| | | |-tickets
| | | | |-2026-09-10-cdm-1317-infrastructure-discovery-server.md
| | |-2026-Q4
| | | |-...
| |-de
| | |-2026-Q3
| | | |-...
|-README.md
|-README.de.md
```

- `pm` هر آنچه را پروژه برنامه‌ریزی می‌کند و می‌نویسد نگه می‌دارد، `doc`
  مستنداتی را که به هیچ فصلی تعلق ندارند. هر دو برای هر زبان یک پوشه
  دارند، [زبان‌ها را نگه دار](#keep-the-languages) را ببین
- در `pm/<lang>` همه چیز در یک پوشهٔ فصل `<yyyy>-Q<n>` قرار دارد که در
  ادامه `pm/<lang>/<quarter>` نامیده می‌شود. هیچ چیز از آن کنار پوشه‌های
  فصل نیست، تا مخزن در طول سال‌ها حجیم‌تر و دشوارخوان‌تر نشود: جدیدترین
  پوشهٔ فصل همهٔ آنچه هنوز معتبر است را دارد، قدیمی‌ترها تاریخچه‌اند
- جدیدترین پوشهٔ فصل، فصل جاری است. فقط آن‌جا بخوان و بنویس؛ هرگز فصل
  قدیمی‌تری را تغییر نده
- آنچه در پایان یک فصل هنوز معتبر است به فصل بعد رونویسی می‌شود،
  [فصلی را آغاز کن](#start-a-quarter) را ببین
- `doc/<lang>/guides` و `doc/<lang>/templates` از لایه‌های DNA می‌آیند؛
  هرگز ویرایششان نکن
- `README.md` پروژه را نام می‌برد و به فصل جاری، هدف‌های فعال و
  نیازمندی‌هایش پیوند می‌دهد
- `architecture` — تصویر هدف سیستم: `architecture.md` به‌علاوهٔ نمودارهایی
  در `img` به شکل فایل‌های mermaid با پسوند `.mmd`
- `blog` — برای هر تیکت تمام‌شده یک پست؛ فقط وقتی وجود دارد که مخزن
  `doc/en/guides/blog-guide.md` را از لایهٔ `dna_blog` داشته باشد، پایین را
  ببین
- `bugs` — برای هر باگ یک فایل؛ باگ وقتی برنامه‌ریزی شد به تیکت تبدیل
  می‌شود
- `charts` — برنامهٔ زمانی `schedule.md` و هر نمودار دیگر فصل،
  [نمودار رسم کن](#draw-charts) را ببین
- `concepts` — محصول چیست و چرا: `topics`، `decisions` و `ux`، پایین را
  ببین
- `exports` — فایل‌های CSV تیکت‌ها برای Jira،
  [تیکت‌ها را به Jira صادر کن](#export-tickets-to-jira) را ببین
- `goals` — پروژه می‌خواهد به چه برسد و برای چه کسی؛ برای هر هدف یک فایل،
  پایین را ببین
- `meetings` — برای هر جلسه یک فایل،
  [جلسه‌ها را ثبت کن](#keep-the-meetings) را ببین
- `prompts` — پرامپت‌هایی که ارزش نگه‌داشتن دارند، مثلاً پرامپتی که یک تیکت
  را آغاز کرد؛ برای هر پرامپت یک فایل، `<yyyy>-<mm>-<dd>-<title>.md`
- `reports` — برای هر نفر یک گزارش با نکته‌هایی که باید به او گفته شود،
  [به افراد گزارش بده](#report-to-the-people) را ببین
- `requirements` — محصول چه باید بکند یا چه باید باشد؛ برای هر حوزه یک
  فایل، پایین را ببین
- `team` — چه کسی و در چه نقش‌هایی روی پروژه کار می‌کند،
  [تیم را بشناس](#know-the-team) را ببین
- `tickets` — برای هر تیکت یک فایل برنامه

## هدف‌ها و نیازمندی‌ها را از هم تشخیص بده <a id="tell-goals-and-requirements-apart"></a>

- هدف می‌گوید **چرا** و **برای چه کسی**: نتیجه‌ای که پروژه می‌خواهد، مثلاً
  «باشگاه‌ها مسابقه‌هایشان را بدون نرم‌افزار دسکتاپ ارزیابی می‌کنند». باز
  می‌گذارد که چگونه به آن برسیم و وقتی نتیجه حاصل شد، تمام است
- نیازمندی می‌گوید محصول **چه** باید بکند یا باشد: گزاره‌ای آزمون‌پذیر
  دربارهٔ سیستم، مثلاً «فهرست نتایج دو ثانیه پس از رسیدن آخرین شرکت‌کننده
  آماده است». چیزی دربارهٔ چگونگی ساختنش نمی‌گوید و تا وقتی تغییر نکرده یا
  کنار گذاشته نشده معتبر است
- تیکت می‌گوید **چگونه** و **کی**: گامی که نیازمندی‌ها را در خدمت یک هدف
  برآورده می‌کند
- موضوع‌ها (topics) فضای مسئله را نگه می‌دارند — شواهد و نیازهای کاربر.
  نیازمندی‌ها تعهدهایی هستند که از آن‌ها استخراج می‌شوند؛ نیازمندی‌ها را در
  موضوع‌ها ننویس
- هدف‌ها و نیازمندی‌ها از فصل‌ها فراتر می‌روند: یک هدف ممکن است چند فصل
  طول بکشد، یک نیازمندی تا وقتی محصول هست معتبر است. به همین دلیل
  موارد باز به هر فصل تازه رونویسی می‌شوند،
  [فصلی را آغاز کن](#start-a-quarter) را ببین

## هدف‌ها را بنویس <a id="write-the-goals"></a>

- `pm/<lang>/<quarter>/goals/<title>.md` را بساز، عنوان به انگلیسی و به شکل
  kebab case
- این بخش‌ها را به همین ترتیب به کار ببر:

```markdown
# <Title>

## Status

## Outcome

## Measure

## Requirements
```

- `Status` — `proposed`، `active`، `reached` یا `dropped`، به‌علاوهٔ
  فصل‌هایی که روی هدف کار شد، مثلاً `active since 2026-Q3`. هدف تا وقتی
  تیم تأییدش نکرده `proposed` است
- `Outcome` — یک بند: چه چیزی تغییر می‌کند، برای چه کسی، و چرا اهمیت دارد
- `Measure` — از کجا بدانیم هدف محقق شده است
- `Requirements` — پیوند به نیازمندی‌هایی که از هدف استخراج شده‌اند
- هرگز هدفی را پاک نکن؛ آن را `reached` یا `dropped` کن و دلیلش را بگو

## نیازمندی‌ها را بنویس <a id="write-the-requirements"></a>

- نیازمندی‌ها را بر اساس حوزهٔ محصول گروه‌بندی کن، برای هر حوزه یک فایل:
  `pm/<lang>/<quarter>/requirements/<area>.md`، حوزه به انگلیسی و به شکل
  kebab case
- به هر نیازمندی یک شناسهٔ `req-<area>-<nnn>` بده، مثلاً `req-results-001`؛
  پیشوند آن را از شناسه‌های تصمیم جدا نگه می‌دارد. هرگز شناسه‌ای را دوباره
  به کار نبر یا شماره‌گذاری دوباره نکن. شناسهٔ تازه پس از بالاترین شناسهٔ
  آن حوزه در همهٔ فصل‌ها می‌آید، چون نیازمندی‌های انجام‌شده در فصل‌های
  قدیمی‌تر باقی می‌مانند
- هر نیازمندی را به‌صورت یک بخش جداگانه بنویس:

```markdown
## req-results-001: Result list right after the race

- Status: accepted
- Priority: must
- Statement: The result list is ready two seconds after the last finisher
- Why: [results without desktop software](../goals/results-without-desktop-software.md),
  topic `timing`
- Acceptance: a race with 500 finishers shows the list within two seconds
```

- `Status` — `proposed`، `accepted`، `done` یا `dropped`
- `Priority` — `must`، `should` یا `could`؛ آنچه اصلاً خواسته نیست
  `dropped` است
- `Statement` — یک جمله دربارهٔ این‌که محصول چه باید بکند یا باشد، هرگز
  چگونه
- `Why` — هدفی که به آن خدمت می‌کند و موضوعی که از آن آمده
- `Acceptance` — آزمون‌هایی که آن را اثبات می‌کنند؛ در صورت نیاز برای هر
  آزمون یک بولت
- نیازمندی را در همان جا تغییر بده و بگو چه چیزی و کی تغییر کرد؛ نیازمندی‌ای
  که جایگزین می‌شود `dropped` می‌شود و به جانشینش پیوند می‌دهد
- نیازمندی `done` که خراب شده یک باگ است، نه نیازمندی تازه

## اول نیازمندی‌ها را استخراج کن <a id="engineer-the-requirements-first"></a>

- هدف‌ها و نیازمندی‌ها را همراه با کاربر پیدا کن، هر بار یک پرسش و با
  پیشنهاد: [راهنمای نیازمندی‌ها](requirements-guide.md) می‌گوید چگونه،
  `/gg-plan-requirements` آن را اجرا می‌کند
- این کار را پیش از نخستین تیکت انجام بده، هر وقت
  `pm/<lang>/<quarter>/requirements` خالی است، و هر وقت کار یک تیکت را هیچ
  نیازمندی پذیرفته‌شده‌ای پوشش نمی‌دهد
- فقط پس از آن تیکت‌ها را برنامه‌ریزی کن و بساز. تیکت‌های باگ استثنا
  هستند: به‌جای آن فایل باگ خود را نام می‌برند
- `/gg-plan-intro` مهارت‌های (skills) برنامه‌ریزی را فهرست می‌کند و می‌گوید
  کدام بعدی است

## تیم را بشناس <a id="know-the-team"></a>

- بنویس چه کسی روی پروژه کار می‌کند در `pm/<lang>/<quarter>/team/people.md`،
  برای هر نفر یک بخش:

```markdown
# People

- Sprint length: 2 weeks
- Hours per day: 8

## Anna

- Areas: result list, import of race data, the `timing_app` repo
- Days per week: 4
- Jira: anna
```

- عنوان بخش نام کوچک است؛ نام فایل‌های آن شخص آن را با حروف کوچک و به شکل
  kebab case به کار می‌برند: `anna`
- `Areas` — آنچه شخص مسئولش است: قابلیت‌ها، موضوع‌ها، مخزن‌ها. خروجی Jira
  تیکت‌ها را بر اساس آن‌ها با افراد تطبیق می‌دهد
- `Days per week` — شخص چه بخشی از هفته را روی پروژه کار می‌کند
- `Jira` — نامی که Jira شخص را با آن می‌شناسد: نام کاربری در Jira Data
  Center یا Server، مثلاً `anna`، شناسهٔ حساب Atlassian در Jira Cloud؛
  اختیاری
- `Sprint length` — یک بار، در بالا؛ پیش‌فرض دو هفته
- `Hours per day` — یک بار، در بالا: ساعت‌های کاری یک روز، برای تبدیل
  تخمین‌های روزانه به ساعت؛ پیش‌فرض 8
- نقش‌ها را در `pm/<lang>/<quarter>/team/roles.md` بنویس، برای هر نقش یک
  بخش. با Developer، Product Owner، Management، Sales و Customer شروع کن
  و نقش‌هایی را که پروژه نیاز دارد اضافه کن:

```markdown
# Roles

## Product Owner

- Responsible for: goals, requirements and their priority
- People: Anna
- Hears about: goals, requirements, decisions, schedule shifts
```

- `People` — نام‌های کوچک `people.md` که این نقش را دارند. این تنها جایی
  است که می‌گوید چه کسی چه نقشی دارد؛ `people.md` آن را تکرار نمی‌کند
- `Hears about` تعیین می‌کند چه چیزی در گزارش‌های افراد آن نقش قرار
  می‌گیرد. مشتریان و فروش از نتیجه‌ها و تاریخ‌ها باخبر می‌شوند، هرگز از
  جزئیات داخلی مانند کد، تصمیم‌های باز یا تخمین‌ها
- یک نفر می‌تواند چند نقش داشته باشد و بنابراین زیر چند نقش فهرست شود؛
  گزارش او همهٔ آن‌ها را پوشش می‌دهد
- پیش از نخستین گزارش یا خروجی، تیم را از کاربر بپرس؛ هرگز افراد یا
  نقش‌ها را حدس نزن
- در `team` فقط نام‌های کوچک، حوزه‌ها و نقش‌ها را نگه دار، به‌علاوهٔ حساب
  Jira و نام‌های کاربری git؛ هیچ اطلاعات تماسی
- هرگز نشانی ایمیل نپرس و هرگز یکی را در مخزن PM ننویس، نه در `team` و نه
  هیچ جای دیگر. وقتی کاربر یکی را پیشنهاد می‌کند، به‌جایش نام کاربری git یا
  حساب Jira را بپرس

## پوشهٔ concepts را پر کن <a id="fill-the-concepts-folder"></a>

- `topics` — برای هر موضوع محصول یک فایل: شواهد، موارد کاربرد، نیازهای
  کاربر، آنچه امتحان شد و آنچه معتبر است؛ جای دانش فضای مسئله
- `decisions` — برای هر تصمیم یک فایل، `<area>-<nnn>.md`، مثلاً
  `design-001.md`؛ `000-index.md` همهٔ تصمیم‌ها را با شناسه، وضعیت، تاریخ،
  یک سطر و کار باز فهرست می‌کند
- `ux` — گزاره‌های پذیرفته‌شده دربارهٔ سطح (surface) و جریان‌های محصول:
  کاربر با کدام اشیا، مکان‌ها و واژه‌ها روبه‌رو می‌شود، و چرا
- فایل تصمیم را با این‌ها بنویس: عنوان، وضعیت (proposed / accepted /
  superseded)، تاریخ، منبع مرجع، کار باز، خود تصمیم در یک بند
- هرگز تصمیمی را بازنویسی نکن؛ با تصمیمی تازه جایگزینش کن و در هر دو جهت
  پیوند بده

## پست‌های وبلاگ بنویس <a id="write-blog-posts"></a>

- فقط وقتی پست بنویس که `doc/en/guides/blog-guide.md` وجود داشته باشد؛ از
  لایهٔ `dna_blog` می‌آید. بدون آن هیچ پستی ننویس و بقیهٔ این بخش را رد کن
- برای محتوا و قالب از راهنمای وبلاگ پیروی کن
- پست را در `pm/<lang>/<quarter>/blog` مخزن PM بگذار، در فصل روزی که تیکت
  تمام می‌شود
- نامش را `<yyyy>-<mm>-<dd>-<title>.md` بگذار، عنوان به انگلیسی و به شکل
  kebab case
- یک پست می‌تواند همهٔ مخزن‌های تیکت را که به سازمان مخزن PM تعلق دارند
  پوشش دهد
- فقط دانش سازمان مخزن PM را بنویس
- مخزن‌های سازمان‌های دیگر در ocean را کنار بگذار، حتی اگر در تیکت نقش
  داشتند. آن‌ها را فقط به‌عنوان وابستگی‌های به‌روزشده نام ببر: نام عمومی
  بسته، نسخه و معنای به‌روزرسانی برای مخزن‌های این سازمان؛ هرگز تیکت‌ها،
  برنامه‌ها یا جزئیات داخلی‌شان

## فایل‌ها را نام‌گذاری کن <a id="name-the-files"></a>

- فایل‌های تیکت و باگ را با تاریخ آغاز کن: `<yyyy>-<mm>-<dd>-`
- شناسهٔ تیکت را با حروف کوچک اضافه کن: `cdm-1317`
- با عنوان به انگلیسی و به شکل kebab case تمام کن:
  `2026-09-10-cdm-1317-infrastructure-discovery-server.md`
- هدف‌ها، حوزه‌های نیازمندی، موضوع‌ها، فایل‌های ux، فایل‌های معماری و
  نمودارها را بر اساس موضوعشان، به انگلیسی و به شکل kebab case نام‌گذاری کن
- گزارش‌ها را `<name>.md` و خروجی‌ها را `<yyyy>-<mm>-<dd>-<name>-sprint.csv`
  نام‌گذاری کن، که `<name>` نام کوچک با حروف کوچک و به شکل kebab case است
- نام‌های انگلیسی فایل‌ها را در هر زبان حفظ کن

## جلسه‌ها را ثبت کن <a id="keep-the-meetings"></a>

- برای هر جلسه یک فایل در `pm/<lang>/<quarter>/meetings` بنویس، با نام
  `<yyyy>-<mm>-<dd>-<topic>.md`، موضوع به انگلیسی و به شکل kebab case
- این بخش‌ها را به همین ترتیب به کار ببر:

```markdown
# <Topic> — <yyyy>-<mm>-<dd>

## Participants

## Topics

## Decisions

## Tasks
```

- `Participants` — نام‌های کوچک `team/people.md`، به‌علاوهٔ مهمانان بر
  اساس نقش؛ هرگز اطلاعات تماس
- `Decisions` — برای هر تصمیم یک سطر؛ تصمیمی که به محصول شکل می‌دهد،
  فایل خودش را هم در `concepts/decisions` می‌گیرد
- `Tasks` — برای هر کار یک چک‌باکس با نام کوچک کسی که آن را انجام می‌دهد
- کارهایی را که محصول را تغییر می‌دهند به تیکت تبدیل کن؛ از کار به تیکت
  پیوند بده

## نمودار رسم کن <a id="draw-charts"></a>

- هر نمودار فصل را در `pm/<lang>/<quarter>/charts` بگذار، برای هر نمودار
  یک فایل markdown با نمودار به شکل mermaid، مثلاً برنامهٔ زمانی
  `schedule.md`، یک نمودار burn-down یا توزیع تیکت‌ها
- نمودار را بر اساس موضوعش، به انگلیسی و به شکل kebab case نام‌گذاری کن
- در یک بند بالای نمودار بگو چه چیزی را نشان می‌دهد و از کدام فایل‌ها رسم
  شده، تا بتوان دوباره رسمش کرد
- وقتی منابع نمودار تغییر کرد دوباره رسمش کن؛ هرگز نمودار یک فصل
  قدیمی‌تر را ویرایش نکن

## زبان‌ها را نگه دار <a id="keep-the-languages"></a>

- این مخزن فایل‌هایش را به این زبان‌ها نگه می‌دارد، زبان اصلی اول:
  `dnaLanguages`. متغیر DNA که آن‌ها را تعیین می‌کند در `dna/_vars.json`
  فهرست شده است؛ آن را در `vars` فایل `dna/_dna.json` تغییر بده
- هر فایل `pm` و `doc` برای هر زبان یک بار وجود دارد، زیر `pm/<lang>` و
  `doc/<lang>` با همان مسیر و نام فایل، که `<lang>` کد دوحرفی زبان است
- `README.md` انگلیسی است، هر زبان دیگر `README.<lang>.md` دارد
- فایل زبان اصلی را اول بنویس، حتی اگر کاربر به زبان دیگری صحبت می‌کند،
  سپس زبان‌های دیگر را؛ همه را در همان کامیت تغییر بده
- عنوان‌ها و متن را ترجمه کن. شناسه‌ها، نام فایل‌ها، پیوندها، مقدارهای
  وضعیت و اولویت و نام فیلدهای نیازمندی‌ها را همان‌طور که هستند نگه دار، تا
  هر نسخه برای ابزارها خوانا بماند
- همهٔ نسخه‌ها را از نظر محتوا و ساختار یکسان نگه دار؛ نکتهٔ تیک‌خورده در
  یک گزارش در همهٔ آن‌ها تیک خورده است
- خروجی‌ها را هم ترجمه کن: خلاصه‌ها و توضیحات، هرگز سطر سرستون، کلیدها،
  شناسه‌ها یا نام‌ها را، تا Jira هر کدام را وارد کند
- راهنماها و قالب‌ها در هر زبان از لایه‌های DNA می‌آیند؛ هرگز ترجمه یا
  ویرایششان نکن

## به افراد گزارش بده <a id="report-to-the-people"></a>

- برای هر نفر و هر فصل یک گزارش در `pm/<lang>/<quarter>/reports/<name>.md`
  نگه دار: نکته‌هایی که شخص باید بشنود، هر کدام با یک چک‌باکس که پس از
  اطلاع‌رسانی تیک می‌خورد
- [راهنمای گزارش](report-guide.md) می‌گوید چگونه، `/gg-plan-report` آن را
  اجرا می‌کند: آنچه را برای نقش‌ها و حوزه‌های شخص تغییر کرده جمع می‌کند،
  اضافه می‌کند و فایل فصل تازه را با نکته‌های باز منتقل‌شده آغاز می‌کند

## تیکت‌ها را به Jira صادر کن <a id="export-tickets-to-jira"></a>

- تیکت‌های بعدی یک نفر را به شکل فایل CSV که Jira وارد می‌کند خروجی بگیر:
  `pm/<lang>/<quarter>/exports/<yyyy>-<mm>-<dd>-<name>-sprint.csv`
- [راهنمای خروجی Jira](jira-export-guide.md) می‌گوید چگونه،
  `/gg-plan-jira-export` آن را اجرا می‌کند: تیکت‌های باز بدون کلید Jira را
  بر اساس حوزه‌ها با شخص تطبیق می‌دهد، یک اسپرینت را بر اساس تخمین‌ها پر
  می‌کند و فایل را می‌نویسد
- شخص فقط هنگام خروجی گرفتن واگذار می‌شود، هرگز در فایل تیکت

## از لایه‌های طراحی استفاده کن <a id="use-the-design-layers"></a>

- با هفت لایهٔ طراحی محصول برنامه‌ریزی کن؛ لایهٔ `dna_design_layers`
  [راهنمای لایه‌ها](layers-guide.md)، یک راهنما برای هر لایه و مهارت‌های
  `/layers-*` را فراهم می‌کند
- پیش از برنامه‌ریزی تیکتی که محصول را تغییر می‌دهد، `/layers-orient` را
  اجرا کن؛ لایه‌ای را نام می‌برد که اول به توجه نیاز دارد
- حاصل هر لایه را در مخزن PM بنویس:

| لایه                                       | محل قرارگیری                  |
| ------------------------------------------ | ----------------------------- |
| رفتار مشاهده‌شده، دامنه، نیازهای کاربر      | `concepts/topics`             |
| راهبرد محصول                               | `goals`                       |
| آنچه نیازها و راهبرد به آن متعهد می‌شوند    | `requirements`                |
| مدل مفهومی، جریان تعامل                    | `concepts/ux`, `architecture` |
| سطح (surface)                              | `concepts/ux`                 |
| هر تصمیمی که در مسیر گرفته شد              | `concepts/decisions`          |

- تیکتی را روی لایه‌ای که پایه‌هایش ضعیف است برنامه‌ریزی نکن؛ اول پایه را
  برنامه‌ریزی کن، یا صریح بگو که تیکت یک شرط‌بندی است

## تیکتی را برنامه‌ریزی کن <a id="plan-a-ticket"></a>

هدف را تعیین کن: یک بند دربارهٔ این‌که چه چیزی و برای چه کسی به دست می‌آید،
و به کدام هدف پروژه خدمت می‌کند.

نیازمندی‌هایی را که تیکت برآورده می‌کند با شناسه فهرست کن. اگر هیچ نیازمندی
پذیرفته‌شده‌ای کار را پوشش نمی‌دهد، بایست و ابتدا نیازمندی‌ها را با کاربر
استخراج کن، [اول نیازمندی‌ها را استخراج کن](#engineer-the-requirements-first)
را ببین.

مخزن‌های درگیر و آنچه در هر کدام تغییر می‌کند را نام ببر.

گام‌های کلی را به ترتیب فهرست کن؛ برای هر گام یک سطر.

پرسش‌های باز را جمع کن؛ پیش از پیاده‌سازی با کاربر درباره‌شان تصمیم بگیر.

به هدف‌ها، نیازمندی‌ها، تصمیم‌ها و موضوع‌هایی که برنامه بر آن‌ها تکیه دارد
پیوند بده.

بگذار کاربر برنامه را بازبینی کند و آن را اصلاح کن تا تأییدش کند.

## فایل تیکت را بنویس <a id="write-the-ticket-file"></a>

- `pm/<lang>/<quarter>/tickets/<date>-<id>-<title>.md` را بساز
- این بخش‌ها را به همین ترتیب به کار ببر:

```markdown
# <ID>: <Title>

## Goal

## Requirements

## Affected repos

## Steps

## Open questions
```

- برنامه را کوتاه نگه دار؛ فقط برای تیکت‌های پیچیده بیشتر بنویس
- سطرها را در 80 نویسه بشکن
- وقتی تصویر بیش از متن می‌گوید، نمودارهای mermaid را جاسازی کن

## برنامه را زنده نگه دار <a id="keep-the-plan-alive"></a>

- وقتی پیاده‌سازی از برنامه منحرف می‌شود، برنامه را به‌روز کن
- پرسش‌های پاسخ‌داده‌شده را از `Open questions` به برنامه یا به یک فایل
  تصمیم منتقل کن
- وقتی تیکت تمام شد، نیازمندی‌هایی را که برآورده کرد `done` کن
- تیکت را در `pm/<lang>/<quarter>/charts/schedule.md` با `done` علامت بزن،
  اگر پروژه زمان‌بندی دارد
- در پست وبلاگی که تیکت را می‌بندد به برنامه ارجاع بده
- فایل را نگه دار: برنامه مستند می‌کند چرا چیزها این‌گونه‌اند

## زمان را برنامه‌ریزی کن <a id="plan-the-time"></a>

- برنامهٔ زمانی اختیاری است؛ وقتی کاربر آن را می‌خواهد یا تاریخ هدفی برای
  پروژه نام می‌برد، یکی بساز
- [راهنمای زمان‌بندی](schedule-guide.md) می‌گوید چگونه، `/gg-plan-schedule`
  آن را اجرا می‌کند: تاریخ هدف و ظرفیت را می‌پرسد، نیازمندی‌های
  پذیرفته‌شده را به تیکت‌ها می‌بُرد، هر کدام را تخمین می‌زند و برنامه را به
  شکل نمودار گانت در `pm/<lang>/<quarter>/charts/schedule.md` رسم می‌کند
- زمان را فقط بر پایهٔ نیازمندی‌های پذیرفته‌شده برنامه‌ریزی کن

## فصلی را آغاز کن <a id="start-a-quarter"></a>

پوشهٔ فصل تازه را پیش از نوشتن نخستین فایل آن فصل آغاز کن، مثلاً
`pm/en/2027-Q1` با نخستین تیکت در ژانویه. به کاربر بگو، نشان بده چه چیزی
منتقل می‌شود و آن را جداگانه با پیام `Start <yyyy>-Q<n>` کامیت کن.

آنچه از فصل قبل هنوز معتبر است را رونویسی کن:

| چه چیزی                      | آنچه به فصل تازه رونویسی می‌شود                       |
| ---------------------------- | ---------------------------------------------------- |
| `goals`                      | هدف‌های `proposed` و `active`                         |
| `requirements`               | برای هر حوزه، نیازمندی‌هایی که `done`/`dropped` نیستند |
| `team`                       | همه چیز                                              |
| `architecture`               | همه چیز                                              |
| `concepts/ux`                | همه چیز                                              |
| `concepts/decisions`         | `000-index.md` بدون تصمیم‌های جایگزین‌شده              |
| `charts/schedule.md`         | تیکت‌هایی که `done` نیستند، یک `History` تازه          |
| `reports`                    | نکته‌های باز، با `/gg-plan-report`                    |

تیکت‌ها و باگ‌های باز را با `git mv` به `tickets` و `bugs` فصل تازه منتقل
کن: تیکت تا وقتی باز است که در زمان‌بندی `done` نباشد و همهٔ نیازمندی‌هایش
`done` نباشند؛ در صورت تردید از کاربر بپرس. این تنها تغییر در یک فصل
قدیمی‌تر است.

بقیه را همان جا که نوشته شده رها کن: موضوع‌ها، فایل‌های تصمیم، تیکت‌های
تمام‌شده، پست‌های وبلاگ، جلسه‌ها، پرامپت‌ها، خروجی‌ها و نمودارهای غیر از
زمان‌بندی. فصل تازه بدون آن‌ها آغاز می‌شود و به آن‌ها در فصل قدیمی‌تر پیوند
می‌دهد، مثلاً `../../2026-Q4/concepts/decisions/design-001.md`.

- پیوندهای فایل‌های رونویسی‌شده و منتقل‌شده را اصلاح کن: پیوندهای درون فصل
  همان‌طور که هستند می‌مانند، پیوندها به آنچه باقی ماند به فصل قدیمی‌تر اشاره
  می‌کنند
- حوزه‌ای از نیازمندی‌ها را که همهٔ نیازمندی‌هایش `done` یا `dropped` است
  کنار بگذار؛ شناسه‌هایشان همچنان گرفته شده می‌مانند
- فصل تازه را به `Status` هدف‌های منتقل‌شده اضافه کن، مثلاً
  `active since 2026-Q3`
- `README.md` را به فصل تازه ارجاع بده
- همین کار را در هر زبان مخزن انجام بده

## فصلی را برنامه‌ریزی کن <a id="plan-a-quarter"></a>

ابتدا پوشهٔ فصل را آغاز کن، [فصلی را آغاز کن](#start-a-quarter) را ببین.

هدف‌هایی را که فصل روی آن‌ها کار می‌کند انتخاب کن: هدف‌های تازه را به
`goals` اضافه کن، هدف‌های منتقل‌شده را وقتی محقق یا کنار گذاشته شدند
`reached` یا `dropped` کن.

نیازمندی‌ها را همراه با کاربر از هدف‌ها و موضوع‌ها استخراج کن؛ نیازمندی‌های
تازه را اضافه کن و آن‌هایی را که هدف‌ها تغییرشان می‌دهند تغییر بده.

وقتی هدفی تصویر هدف را تغییر می‌دهد، `architecture/architecture.md` را
به‌روز کن.

تیکت‌ها را از نیازمندی‌ها استخراج کن؛ هر تیکت هدفی را که به آن خدمت می‌کند
و نیازمندی‌هایی را که برآورده می‌کند نام می‌برد.

`charts/schedule.md` را به‌روز کن، اگر پروژه آن را دارد، و پیش‌بینی را با
تاریخ هدف مقایسه کن.

`team` را بررسی کن و گزارش‌های فصل را با `/gg-plan-report` آغاز کن؛ این
مهارت نکته‌های باز فصل گذشته را منتقل می‌کند.
